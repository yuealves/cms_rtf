# 20261013：内存内窗口聚合，取消逐股中间文件

验收代码：`30df4b5`，分支 `perf/in-memory-aggregate-20261013`。
对照为上一版低内存内核 `880eff2`，不是最初约 23 GiB 的全天 vector 版本。
[完整机器可读结果](20261013-in-memory-aggregate.json) 保存命令、各轮计时、RSS、
106 列逐列检查及健康计数。结果通过；没有修改线上组件。

## 改动及华泰对应关系

参考 Huatai `light_rtf_v2` 的 `546aba2fa733d4f7f7656af0572115287418b12d`：
`worker.cpp:286–352` 的关窗/贡献消费、`BuildContribution` 的捕获回收及
`AggregateEmit` 的固定成分股顺序。新的默认 journal replay 链路为：

```
DTYPE 输入 → C++ 每股簿/流量 → 待关窗贡献 → 按 symbol 升序聚合 → 最终 Arrow
```

逐股贡献消费后移出缓存；每股保留当前捕获和上一 midpoint，指数仅保留最近
10 个 Float32 流量桶，按时间顺序用 Float64 重算 5s 和。聚合公式和 Arrow 输出
抽为共享 C++ 模块，旧文件聚合器仍可用于对照。106 列、右闭网格、量化点及
固定股票加权次序保持原有契约。

默认路径不再产生 `w*.book.cmsb`、`w*.flow.cmsb` 或 `w*.seeds.bin`，也不在 EOF
回读这些文件。仍有小型权重/阈值输入及诊断日志。运行中 `.tmp.PID` 的内容就是
最终 Arrow；成功后 rename，不是另一套逐股历史，也不产生第二份完整复制。
Python 驱动必须等 exporter 和 C++ 都成功才替换正式输出，失败保留旧文件。

## 验证范围与计时

- gy_dev：同日全天 `/tmp/par_t8.bin`，68,570,400,648 字节，535,706,255 条原始

- 都是 16 worker、`--window-batch 64`。该参数批量调度关窗，仍逐 500ms 端点计算。
- 复用已导出的同一 DTYPE 输入，**没有运行 exporter**。旧侧为内核与聚合两个顺序
  执行的 C++ 进程；新侧一个进程完成计算、聚合及 Arrow。墙钟从进程启动至退出，
  旧侧两段相加；不包含参考准备和事后对拍。

  `-DCMAKE_CXX_FLAGS=-D_GLIBCXX_USE_CXX11_ABI=0`，对应当地 Arrow 的旧 ABI。

## 内存保留了什么

新旧版 EOF 均有 64,886,586 个 SH 全天订单身份、4,172,008 个活跃委托。
压缩身份表容量仍为 2,840,256,512 B（约 2.645 GiB），没有通过删除历史身份
改变委托计数、累计量或大小单分类。

新侧各 worker 的待聚合 payload 各自峰值之和为 156,385,176 B（约 149.1 MiB）；
这不是同一时刻的全局堆快照。消费完成后的输出 vector 容量为 133,296,640 B。
另有活跃簿、SPSC ring、输入缓冲、Arrow 和分配器等。实测全进程峰值为约
3.23 GiB，比上一版约 3.46 GiB 还低约 6.5%。

`--pending-mib 256` 是全体 worker 共享的待聚合额度上限；以 64 KiB 额度批量
领取，避免每条记录都争抢原子计数。它不是全进程 RSS 上限。超额会明确失败，
不会覆写旧数据、丢事件或改成磁盘溢出。异常大 vector 在消费后回收多余容量。

## 全天实验揭示的边界与修正

收盘时有通道停在 14:56:59.990，随后跳到 15:00；然而输入末尾还有约 24,976 条
成分股记录早于 14:59:59.500。每通道最大时间的最小值在此处不足以证明尾批完整。
直接使用 Huatai 的通道有序前提，会过早关窗；照 Huatai 抑制这些迟到流量又会
改变原 CMS 离线结果。

新路径因此保留会话末最后一次水位跳跃：午间等下一会话，收盘等正常 EOF，再
消费尾批。使用现有 AM/PM 会话常量，不额外改因子公式或模拟墙钟超时。日内
若事件真的落后于已发布窗口，明确报错并拒绝发布正式文件。
初版 128 MiB 均分线程的预算也因此不合适；现在使用共享的固定 256 MiB 额度。

第一个完整正确版本 `9bde7b1` 测得 72.048 / 78.338 秒，性能未验收。进一步
将空队列的持续 yield 改为短暂自旋后 25 微秒等待，并将各 worker 的预算计数器
按 cache line 隔离。示例进程的系统 CPU 累计时间从 527.32 秒降到 27.96 秒；
最终性能数据对应 `30df4b5`。读入、映射、屏障和聚合现均有独立阶段计时。

## 正确性与复现

所有最终本地/全天轮次与旧版及此前验收的 CMS Arrow 比较：

- 115,200 行，键相同且唯一，106/106 列有效值 Float32 位模式与 null mask 相同。
- 事件数、簿健康计数、SH 身份数、活跃委托数相同。
- 本地和 gy_dev 都通过 5 项 CTest 与 41 项 Python unittest；关闭 Arrow 构建选项
  后的两个内核入口仍能编译。
- 新测试覆盖安静股票、午休、收盘尾批、不同线程/调度批次、输入未 EOF 时输出、
  水位停滞、预算共享及超限、输入截断、迟到拒绝和 producer 失败不替换旧输出。

命令与参数保存在 JSON 各 run 的 `command`；运行方式见
[操作说明](../how-to.md#journal-replay-与性能对拍)。主要验收文件：

本次改动完成了引擎内的窗口聚合与输出内存优化；验证入口仍为 journal replay。
没有新增 journal 实时 follower 或会话定时器，也没有把此次回放 RSS 宣称为
已上线实盘的现场测量。逐可用端点调度参数为 `--window-batch 1`；其调度开销
与本表的批量 replay 参数应分别衡量。

|---|---:|---:|---:|---:|
| `--window-batch 1` | 51.005 s | 3.203 GiB | 93,318,464 B | 0 B |

因此 36.7 秒应标为批量 replay 吞吐，不能当成逐窗口调度成绩；逐窗口模式通过
