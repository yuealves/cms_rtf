# 回放链路全天验证与性能报告（2026-10-09 数据，2026-10-13 跑）

## 链路（按用户拍板：不走 UDP 回放）

```
v2 parquet → parquet_to_replay.py（numpy 向量化编码 EFH 报文 → CMSREP1 缓存）
  → cms_cache_replay（C++ 缓存直写 journal，跳过 UDP/网关）
  → cms_journal_replay --speed 0（journal→journal 全速回放）
  → cms_journal_export（journal → DTYPE 行流）
  → cms_index500ms_mt（reader 线程 + symbol hash 分发 + N worker 每股状态机）
  → Python 聚合（symbol 升序）→ index_500ms_exch.arrow
```

## 正确性（三层）

| 对拍 | 结果 |
|---|---|
| 回放 MT 版 vs 直读 parquet 版 | **106/106 列逐位一致** |
| 回放 MT 版 vs 华泰参考（exch 网格） | 104/106 列 corr>0.99（与直读版持平） |
| **worker=1 vs worker=8** | **逐字节一致**（light_rtf 位级一致不变量） |

回放 journal 的 journal_check：5.357 亿业务事件、0 丢包、0 坏包、0 缺口、
类型计数与生产 journal 完全一致。

## 性能（r7525，全天 535M 事件）

| 阶段 | 耗时 | 吞吐 | 说明 |
|---|---|---|---|
| parquet→缓存编码（Python 向量化） | ~13 min | ~40MB/s | 一次性，缓存可复用 |
| 缓存→journal（cms_cache_replay） | 116 s | 362k rec/s | 纯顺序 IO+memcpy |
| journal 全速回放（cms_journal_replay） | 169 s | 248k rec/s | 读+校验+重写 |
| journal→DTYPE 行流（cms_journal_export） | ~17.5 min | — | **当前瓶颈**（单线程解析） |
| MT 内核 workers=1（含成分股过滤） | 431 s | — | 基线 |
| MT 内核 workers=8 | **199 s** | 2.3M ev/s | reader 线程成新瓶颈 |
| Python 聚合 + arrow 写出 | ~76 s | — | 与 worker 数无关 |

合计（缓存就绪后）：约 25 分钟/天。**下一步提速候选**：journal 按页并行解析
（格式允许，页自描述+帧自哈希，见当日讨论记录）、reader 分块并行。

## 过程缺陷记录（已修复）

1. MT 引擎初版每股记录按到达序交错落盘 → 聚合层按组连续假设被破坏且慢 100 倍；
   改为每股内存缓冲、worker 结束时按 symbol 升序连续落盘（runner.h 缓冲化）。
2. `std::hash<int>` 对整数是恒等，`sym % 8` 分布倾斜 → 换 multiply-shift 混合器。
3. MT 初版未过滤成分股（白跑 3 亿非成分股事件）→ reader 侧 thresh 表过滤。
4. ` JournalWriter` 需要 paged 在场（"private paged socket missing"）——
   离线写 journal 也要先起 paged。
