## 正确性与实现边界

三轮每版输出、上述实际链路输出，均与上一轮已验收 Arrow 的 106/106 Float32
有效值位模式、null mask、schema、行键和行序完全一致，115,200 行且无重复键。
4 项 CTest 和 32 项 Python unittest 通过。新增差分测试覆盖缺失股票、空 worker、
覆盖门、无效 midpoint、前值不回退、午休、重复/乱序流量端点、分片/股票顺序、
参考版本/截断输入拒绝、写盘失败保留旧输出等。

实现保留官方分母的既有 Float64 值、股票升序、乘法/加法分离、Float32 量化点和
滚动窗无减法语义。C++ 使用固定读缓冲及一只股票的记录，聚合后以 Arrow C++ 分批写出。
Python 只负责小规模参考表准备和进程编排；三个日跑驱动默认使用 C++，
`--aggregate-backend python` 保留对照路径。没有改变逐笔内核、记录 ABI 或因子公式。

## 全天 22.9 GiB 是什么

之前表格的 22.9 GiB 是 **cms_index500ms_mt 逐笔 C++ 进程**的峰值，
不含后续 Python 聚合，更不含上游 exporter 的进程。各阶段分开计量，不能把
它们的 RSS 简单相加当作当时的同时峰值。

读取 gy_dev 已有全天结果的文件大小（未重跑全天）可核实：

| 内核累积的输出 | 记录数 | 数据本体 |
|---|---:|---:|
| 盘口 BookRec280 | 51,724,800 | 14,482,944,000 B = **13.488 GiB** |
| 流量 FlowRec176 | 32,750,363 | 5,764,063,888 B = **5.368 GiB** |
| 合计 | | **18.856 GiB** |

1,796 只有事件的股票 × 28,800 全天端点 × 280 B，恰好就是盘口记录量。
`runner.h:118–129` 持续 push_back；`cms_index500ms_mt.cpp` 的每股 book/flow
vector 要到 EOF 的 finish_all 才写出、删除。因此内存随一天内的端点历史累积，
即使一分钟没有新盘口，也会为网格沿用值写出完整 280 B 记录。

此外还有 vector 未使用容量/扩容瞬时拷贝、分配器保留空间、当前订单簿与哈希节点、
SH 全天委托身份表等。以本构建的 vector 倍增容量为例，28,800 条对应容量 32,768，
仅盘口 vector 的分配容量约 **15.347 GiB**。这是容量量级，不等同于各页实际驻留 RSS；
不能用文件大小减峰值精确反推出订单表内存，需要堆剖析才能做到精确归因。
相比之下 8 个 SPSC 队列总共约 28 MiB，输入读缓冲 8 MiB，线程队列不是主要来源。

前缀测试中实际发生的桶少，EOF 才延续到全天；上一轮“每股写完立即释放”避免所有
股票同时补满全天，所以内核峰值约 1.4 GiB。全天运行时大部分全天记录已在读完前
累积，所以这个释放优化无法消除 22.9 GiB 的峰值。

## 与华泰的差异、这次解决了哪部分

华泰 `worker.cpp:392–399` 取走端点捕获后即 erase，流量贡献和跨 worker 槽位也会清理；
Arrow sink 在关窗后 flush/清空输出缓冲。它主要保留当前簿、待发布窗口及必须保留的
委托身份，不像当前 CMS 批处理那样保留逐股整天输出。

不过华泰同一仓库的 `docs/design/families/index_500ms.md:154` 也记录过
2026-08-28 全天 8 线程峰值约 18 GB，文档将其归于 SH 全天跟踪及双网格状态。
这和 CMS 的日期、行情量、单双网格、输入口径不同，不能直接把差值全归因于某一实现。
不能据此断言华泰当前同日一定只有几百 MB。

Python 原聚合在 mmap 扫描后，文件映射页会计入该进程 RSS；本地前缀测到约
13.7 GiB。C++ 固定缓冲读取消除了长期持有全日文件映射，约 165 MiB RSS 已包含
四指数全天累加器、最终因子和读写缓冲。内核文件 cache 仍可能保留在操作系统中，
所以这是进程 RSS 的下降，不能当成操作系统总内存下降同样的数值。

**本轮解决聚合时间和聚合进程的 RSS；全天逐笔内核的历史结果缓冲仍在。**
下一步若要降低那部分，应将逐股 book/flow 输出改成有界分块写出/消费，保持股票聚合
次序和当前批处理迟到口径；直接照搬实时水位关窗可能改变结果，需要单独验证。
