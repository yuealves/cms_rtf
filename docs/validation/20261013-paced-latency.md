只统计 `(09:30:00,09:45:00]` 的非空、watermark 窗口，两侧均为 1,800 窗、
1,705 次实际关窗。没有按同批窗口数摊薄耗时，也不把历史 recv_ns 到当前墙钟
的时差作为实盘延迟。Arrow 完成指 batch 可读，不代表 fsync 至物理介质。

`app/cms_index500ms_mt.cpp` 的 advance_clock 每推进 500 ms 源时间才检查水位；
5× 下相邻检查约隔 100 ms 墙钟。全速回放同时压缩了等待后续行情和下一轮检查
的时间，因此全速 read-to-write 不能直接预测实盘。

以 last_recv_ns 估算“到下一次 500 ms 源时钟检查”的间隔再除以 5，平均为
62.793 ms，实测 read-to-close 为 63.222 ms，平均残差 0.429 ms；1,637/1,800
窗的差在 2 ms 内。这是辅助估算，不把 gateway recv 与实际 reader 时刻混为一谈。
例如 09:35:00.500 窗：原始最后 recv 为 09:35:00.675029269，等到下一轮
09:35:01.000 检查约需 64.994 ms；实测关窗前 65.678 ms，关窗后 1.474 ms，
合计 67.152 ms。主要延迟来自关窗调度，计算输出仍在约 2 ms 量级。
本次没有修改关窗触发方式，也没有据此直接外推 1× 的实盘分位数。

## 与华泰日志的口径复核

再次只读核对线上 Huatai `546aba2`：`family.cpp:22–35` 同样使用 500 ms 接收
时钟检查点；`engine.cpp` 在 frame.nano 越过检查点时调用 CloseOne，随后
`worker.cpp:296–310` 才按跨通道水位决定可发布的交易所端点。因此不能把这种
等待认定为 CMS 独有缺陷，或仅凭 64.968 ms 判定 CMS 比华泰的几毫秒慢。

Huatai `CloseOne → RecordFire` 才开始 steady_clock 计时，
`ArrowStreamSink::MarkCutoffComplete` 先 Flush local/exch 双流，再 RecordWriteDone，
除以 1e6 输出 ms。此前等待下一条行情、接收时钟检查点及交易所水位的时间没有
计入该日志。CMS `latency.log/close_to_write_ms` 的起止边界属同一类；
`last_read_to_write_ms` 额外包含关窗前等待，华泰现有日志没有这个对应量。

还有采样单位差异：华泰每次引擎 cutoff 记一行，时间标签是该次接收时钟检查点；
CMS 每个实际写出的交易所端点记一行，同一 close_id 可含多个端点。若按实际
关窗去重，本次 CMS 为 1,705 次，mean 1.583 ms、P99 2.336 ms；此前 1.746 ms
是按 1,800 个交易所窗口统计的均值。当天华泰同一 09:30–09:45 区间原日志
1,800 次，mean 6.655 ms、P99 14.009 ms。两边起止点可以对照，但输出工作量
（华泰双网格/CMS 仅 exch）、有效关窗样本及实盘/5× 回放工况仍不同，不能直接
作为两套引擎的性能排名，更不能从这份华泰日志推断最后行情至输出的延迟。

窗边行情的自然间隔确实属于 read-to-write，但还要区分收到“后续帧”和“满足
关窗条件”。上述 09:35:00.500 窗，最后 recv 后 3.012 微秒就有下一帧，源时间
依然落在下一检查点 09:35:01.000 之前；不能将约 65 ms 全解释成没有后续行情。
本轮只核对并纠正统计说明，没有改变关窗策略或移动计时起点来降低数字。
