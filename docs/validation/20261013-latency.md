## 华泰参考及计时口径

只读检查了 ht_idc / insight_yjj_test 容器中的
`/opt/insight/light_rtf_v2`（HEAD `546aba2`）以及
`/data/shenrun/index_500ms/20261013/latency.log`，没有运行或修改华泰业务进程。
`CloseLatencyRegistry::RecordFire` 在引擎 CloseOne 起点记录单调钟；Arrow sink
在 MarkCutoffComplete 内完成 Flush 后调用 RecordWriteDone，除以 1e6 输出毫秒。
因此日志测的是“关窗触发 → Arrow 写完”，不是“收到窗口最后行情 → 写完”。
两者都很有用，CMS 分别记录，起止点说明见 [design.md](../design.md) 最后一节。

这是今天这一份文件的统计，不把用户此前观察的约 3–4 ms 当作错误。

## 新日志

每次运行的 Arrow 同目录增加三个文件：

- `latency.log`：两列，窗口端点、close_to_write_ms，格式便于 tail。
- `latency.csv`：逐窗口 close/read/recv 三种延迟，以及原始纳秒时间戳、事件数、
  mode、phase、reason、close_id、flush_id。
- `latency.meta.json`：schema、毫秒单位、exch 网格和各时间边界定义。

实际 Arrow 每次 WriteRecordBatch + Flush 返回后回调，自动 1024 端点刷新也覆盖。
同批多个端点共享真实写出时刻，不用耗时除以端点数来伪造更低的窗口延迟。
只记录有效成分股当前右闭窗口的事件；空窗接收/read 延迟为空，迟到抑制事件不
回写已经发布的窗口。当前 CMS 只有 exch 因子流，不伪造 local 因子或其 latency。

`last_recv_to_write_ms` 从 gateway 的 recv_ns 起算，包含等待和排队；
`last_read_to_write_ms` 从 cms_rtf 看见 committed frame 起算，包含解码和后续等待；
`close_to_write_ms` 从发出关窗屏障前起算。后两者使用单调钟。接收时间用墙钟，
保留负值用于识别校时异常；历史 replay/source 模式的接收延迟为空。
这些都是 batch 已可被读者读取的时刻，没有 fsync，不宣称物理介质持久化时间。

普通水位、上午收尾、下午收尾和 EOF 分组；catchup、tail、replay 分组。
统计脚本默认排除无当前窗口行情的空窗和交易时段之外样本，输出 mean/P50/P95/
P99/P999/max 和超阈值数。详细操作见 [部署说明](../deploy-live.md)。

## 实测结果（均为 8 worker）

以下只列正常水位关窗，收盘/EOF 收尾单列保存在 JSON。**CMS 两台机器的结果
均为不按原速投放的历史追赶/回放，不是开盘期间实盘端到端延迟。**

| 机器与输入 | 样本窗口数 | 关窗至写出 mean / P99 | 读到最后行情至写出 mean / P99 |
|---|---:|---:|---:|
| 本地，10/09 09:35 前 DTYPE | 599 | 2.697 / 4.596 ms | 3.363 / 5.237 ms |
| gy_dev，10/09 全天 DTYPE | 28,439 | 17.461 / 329.706 ms | 22.459 / 446.742 ms |
| 招商机，10/13 全天原始 journal | 28,438 | 1.405 / 2.059 ms | 5.978 / 18.903 ms |

gy_dev 使用独立 worktree `/data/users/linwei/Code/zs_l2/cms_rtf_latency_20261013`，
GCC 11 / Arrow 11 原有环境，`--workers 8 --window-batch 1 --latency on`，
读取预导出的 `/tmp/par_t8.bin`（535,706,255 行）。本轮内核 208.069 秒，进程
起止墙钟 208.526 秒；执行采用 nice 10。运行时采样的 1/5/15 分钟 loadavg 为
734.02 / 538.53 / 339.26。该共享机器当时负载很高，长尾不可作为招商实盘保证。
没有调整机器配置或处理其他进程。产出与已接受 10/09 Arrow 的 106 列、null mask、
键逐位一致。原始记录保存在 `/data/users/linwei/cms_work/latency_20261013`。

招商机使用真实 journal 的 follow+wall 路径，收盘后 21:06:50 启动，
500,061,765 行，内核耗时 255.922 秒，峰值 3,205,620 KiB（3.057 GiB）。
参考文件仍为已验证的 10/09 版本；本轮用相同参考文件对比前一版的 10/13 产物。
全部窗口标记 catchup：last_recv_to_write_ms 是数小时的历史数据年龄，不能拿来
声称当前实盘总延迟。盘中的该项需在实际运行时看 phase=tail 的记录。

招商的下午定时收尾一次关闭 361 个端点，close_to_write 为 103.763 ms；
这些没有混入上表的普通水位样本。该值也没有除以 361，避免掩盖一次批量收尾的
真实可用时刻。设计中既有的收盘等待规则未变。

`6a8b1ad585cbabeb9b3a6da153a39868385771707a828dca8369aae81d853b75`。
